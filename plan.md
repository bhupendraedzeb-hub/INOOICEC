# Invoice Generator & Template Platform — Master Plan (Phases 0–19)

## Context

The repository contains two spec documents — `agent/AGENTS.md` and `agent/PHASE.md` — that define a private, self-hosted invoice management platform for internal business use (explicitly **not** a SaaS product: no subscriptions, no template tiers, no marketplace, no tenant billing).

The core architectural principle demanded by the spec: **Template** (visual layout JSON, versioned) is kept strictly separate from **Invoice Data** (business/customer/items/payments), and a **Renderer** combines the two into HTML/PDF. Editing a template must never change previously issued invoices — each issued invoice pins an immutable `TemplateVersion`. Both spec files require the same 20-phase (Phase 0–19) build order, executed incrementally with verification between phases, ending in a V1 covering everything in `PHASE.md`'s V1 scope list and explicitly deferring the Post-V1 list (quotations, recurring invoices, email/WhatsApp delivery, advanced reports, bulk import/export, accounting integrations, expanded gateways, advanced RBAC).

Two decisions were confirmed with the user up front:
1. **Full 19-phase master plan** (not just a foundation-only plan) — this document covers all phases, with Phase 0–1 detailed enough to start coding immediately and later phases naming concrete entities/endpoints/components so nothing from the spec is silently dropped.
2. **Auth**: NextAuth.js (Auth.js) v5, Credentials provider, Prisma adapter, **database sessions** (not JWT) — chosen for server-side session revocation and a single Postgres source of truth alongside audit logging.

This is a from-scratch build — there is nothing existing to preserve or reuse.

## Database Schema (Prisma)

Key decisions:
- **Role**: simple enum on `User` (`OWNER | ADMIN | STAFF`), not a separate permissions-matrix table — advanced RBAC is explicitly Post-V1.
- All money fields: `Decimal(14,2)` (rates: `Decimal(5,2)`, quantities: `Decimal(14,3)`).
- `Invoice.paymentStatus` is a cached/derived column, always written transactionally alongside `Payment` writes — never hand-editable — so a paid invoice can't silently flip via a UI change.
- `Invoice.invoiceNumber` is nullable + unique, only assigned inside the `/issue` transaction (never on preview).
- `Invoice.templateVersionId` is only set at issue time and is immutable thereafter — PDFs for issued invoices always use the pinned version, never the live template.
- No hard deletes anywhere on `Invoice`/`Payment` — cancellation/void are status flags.

Models: `User`, `Account`/`Session`/`VerificationToken` (NextAuth), `CompanySettings`, `AuditLog`, `ApiKey`, `Customer`, `Product`, `Template`, `TemplateVersion` (immutable once referenced by an `Invoice`), `Invoice`, `InvoiceItem`, `Payment`, `PaymentLink`, `WebhookEndpoint`, `WebhookDelivery` (unique `idempotencyKey` enforces outbound dedupe).

Full field-level schema (as designed) lives in the Phase 1/4/9/10/11/15 deliverables below — `prisma/schema.prisma` is the single file all of these extend incrementally.

## Template JSON Schema

Stored as `TemplateVersion.layout` (`jsonb`), typed in `src/types/template.ts`, validated by Zod before every save.

```ts
type TemplateDocument = {
  page: { size: "A4"; orientation: "portrait" | "landscape";
           marginTopMm: number; marginRightMm: number; marginBottomMm: number; marginLeftMm: number };
  components: ComponentNode[];
};

type ComponentNode = {
  id: string; type: ComponentType;   // text|image|logo|divider|shape|qrcode|header|businessDetails|
                                      // customerDetails|invoiceDetails|itemsTable|taxSummary|totals|
                                      // paymentDetails|signature|terms|notes|footer
  x: number; y: number; width: number; height: number;
  locked: boolean; visible: boolean; zIndex: number;
  props: ComponentProps;             // discriminated union per `type`, includes shared BaseStyle
                                      // (font, size, weight, align, color, background, border, padding, margin)
};

type FieldRef = { kind: "field"; path: string; fallback?: string };  // e.g. "customer.name", "totals.grand_total"
type RichContent = (string | FieldRef)[];
```

Dynamic fields are **never** typed as raw syntax by users. The builder's "Insert Field" picker (sourced from `lib/render/fieldRegistry.ts`, a static registry of every allowed `business.*` / `customer.*` / `invoice.*` / `totals.*` / `payment.*` path) inserts a `FieldRef` chip. At render time, `fieldResolver.ts` walks the document, resolves each `FieldRef.path` against the invoice's render context, formats by declared type (currency/date/text), and substitutes. This same document + resolver combination is what `TemplateRenderer.tsx` uses in all three consumers: builder canvas, invoice preview, PDF print.

## API Architecture

- All endpoints under `/api/v1/...`. **One implementation per resource** — the same route handlers serve both the internal browser UI (session auth) and external API-key clients, avoiding logic drift between "two APIs."
- **Dual auth**: every route starts with `resolveAuth(request)` (`lib/auth/resolveRequestAuth.ts`): checks NextAuth DB session first, else `Authorization: Bearer inv_live_xxx` (hashed lookup against `ApiKey`, scope check, `lastUsedAt` update), else 401. Downstream, a single `authorize(actor, permission)` function handles both role checks and API-key scopes — one permission model, not two.
- **Validation**: every mutating route runs the matching Zod schema from `lib/validation/schemas/*`, the same schema `react-hook-form` uses client-side.
- **Invoice creation/issue/pdf/preview flow** (the most business-rule-dense part of the system):
  1. `POST /api/v1/invoices` — creates `DRAFT`, `invoiceNumber=null`; totals **always recalculated server-side** via the GST engine regardless of client-sent values.
  2. `PATCH /api/v1/invoices/:id` — edits draft, recalculates every time; blocked once not `DRAFT`.
  3. `GET /api/v1/invoices/:id/preview` — pure read/render via current template state; never touches numbering, versioning, or status.
  4. `POST /api/v1/invoices/:id/issue` — the **only** place numbering + version-pinning happen, inside one `$transaction`: reserves the invoice number (see numbering module), snapshots/reuses a `TemplateVersion` and pins `templateVersionId`, sets `status=ISSUED`, writes an audit log entry, enqueues an `invoice.issued` webhook delivery.
  5. `GET /api/v1/invoices/:id/pdf` — always renders from the **pinned** `templateVersionId` for issued invoices.
  6. `POST /api/v1/invoices/:id/cancel` — status flag only, requires reason, never deletes rows.
  7. `POST /api/v1/invoices/:id/duplicate` — new `DRAFT` copy, fresh `invoiceNumber=null`.
- **Invoice numbering** (`lib/numbering/invoiceNumber.ts`): atomic reservation inside the issue transaction via `SELECT ... FOR UPDATE` on a small counter table (prefix, financial year, last sequence), formatted per `CompanySettings.invoiceNumberFormat` (e.g. `INV-2026-0001`).
- **Webhook delivery**: inbound gateway callbacks land on `/api/v1/webhooks` (generic, not vendor-specific), matched to `PaymentLink`s by `externalPaymentId`, with a **DB unique constraint** (not just an application check) preventing duplicate `Payment` rows from the same gateway transaction. Outbound delivery to configured `WebhookEndpoint`s is handled by `lib/webhooks/worker.ts` (HMAC-signed, retry/backoff, dedup via `WebhookDelivery.idempotencyKey`).

## PDF Rendering Approach

1. `src/app/internal/render/[invoiceId]/route.ts` — server-only route (internal-token-gated, not publicly exposed) that assembles the render context and server-renders `<TemplateRenderer>` to full HTML with print CSS, using the pinned `TemplateVersion` for issued invoices or the live template for drafts.
2. `lib/pdf/printInvoice.ts` launches Playwright, navigates to that internal route, waits for fonts/images/QR, calls `page.pdf({ format: "A4", printBackground: true, margin: {...} })`.
3. **Multi-page item tables with repeated headers**: standard `<table>`/`<thead>` print CSS (`display: table-header-group`) — native browser behavior, no special-casing needed — combined with `break-inside: avoid` on row groups and totals blocks.
4. **Preview reuse**: the invoice creation page's center live-preview pane is an `<iframe>` pointed at the exact same internal render route used for PDF generation, so preview and PDF are guaranteed identical (literally the same HTML; PDF just adds the print step).

## GST & Calculation Engine

Single pure module, `src/lib/calc/gstEngine.ts` — no DB/Next.js imports, fully unit-testable, decimal.js throughout.

- `calculateLine(input)`: per-line `lineSubtotal = qty*rate`, `discount`, `taxableAmount`, `taxAmount = taxableAmount * gstRate/100`, `lineTotal`.
- `calculateInvoiceTotals(lines, ctx)`: sums lines; `isInterState = companyStateCode !== customerStateCode`; same-state splits each line's tax into `cgst = tax/2, sgst = tax/2`; inter-state puts it all in `igstTotal`. Verified against the spec's worked examples: same-state 50,000 subtotal + 9%/9% CGST/SGST = 59,000; inter-state 50,000 + 18% IGST = 59,000.
- **Rounding**: round once, at the end, to 2 decimals (`ROUND_HALF_UP`, overridable constant); the delta is stored as an explicit, auditable `roundOff` line — never round per-line and re-sum.
- `derivePaymentStatus(grandTotal, paidTotal, dueDate, now)`: `PAID` if `paid >= total`; else `PARTIALLY_PAID`/`UNPAID` by `paid > 0`; `OVERDUE` overrides unpaid/partial once `now > dueDate`. Called transactionally on every `Payment` write, and recomputed on dashboard/list reads for the time-dependent `OVERDUE` transition (a cron-only update would lag).

## Risks & Limitations (flagged up front, not silently deferred)

1. **Playwright/Chromium in Docker** — real memory footprint (~100–300MB/instance) and native dependency weight. Mitigation: official Playwright base image, reuse one long-lived browser instance with per-request pages, cap concurrent PDF renders.
2. **Builder-canvas vs print fidelity gap** — even with a shared renderer, browser vs headless-Chromium font/CSS differences can creep in. Mitigation: bundle/self-host fonts (don't rely on OS-installed fonts), keep print media rules always-active in the builder preview, not toggled.
3. **Decimal boundary risk** — any accidental `Number()` coercion when a Decimal crosses the API boundary reintroduces float error. Mitigation: serialize money as strings in Zod schemas/JSON responses, parse back to `Decimal`, only format to display strings at the final render step.
4. **Dual-auth consistency** — session vs API-key enforcement must be uniform. Mitigation: a mandatory `withAuth(handler, { requiredScope })` wrapper every `/api/v1` route uses, plus a Phase 17 test asserting every mutating route rejects unauth/under-scoped requests.
5. **Webhook idempotency** — both inbound (gateway→us) and outbound (us→integrations) dedup must be DB-constraint-backed, not just application-logic, to survive concurrent duplicate callbacks. Explicit test coverage required (Phase 17).
6. **Scope creep** — this is a large, 20-phase spec. Biggest execution risk is over-building (e.g. a generic plugin system, full RBAC) beyond V1. Mitigation: strict phase-by-phase sequencing with a done-checkpoint before advancing; Post-V1 list stays out of bounds unless the user explicitly pulls something forward.
7. **In-app cron/queue simplicity** — no dead-letter visibility beyond the `WebhookDelivery` table, no horizontal scaling. Acceptable for a self-hosted single-instance deployment; flagged as a known limitation.
